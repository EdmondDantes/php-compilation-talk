# Goro: обзор

Написано 29 августа 2026 года по исходникам репозитория `KarpelesLab/goro`
на коммите `6291adc` от 26 мая 2026 года — последнем в ветке `master`.
Лицензия BSD-3, 695 звёзд, 33 форка, 35 подписчиков, 3 открытых issue
(снято через GitHub API 29 августа 2026). Тегов нет, релизов нет.
Автор — Mark Karpelès (1645 коммитов из 1924), второй участник —
Ronald Casili (278 коммитов).

Числа, снятые своими прогонами, помечены датой и окружением. Прогоны
шли на WSL Ubuntu 24.04, Go 1.25.3, `CGO_ENABLED=0`, свежий клон
`6291adc`; для сравнения использован PHP 8.5.1 (Windows, релизная
сборка, ключ `-n`, та же машина).

## Что это

Движок PHP на Go: свой лексер, свой парсер в AST, свой компилятор в
стековый байткод и своя виртуальная машина. Zend не используется вовсе —
в отличие от TypePHP, который линкует `libphp` и компилирует поверх
движка. 171 227 строк Go в 428 файлах вне каталога с тестами.

Заявка README: «PHP engine implemented in pure Go. Feature-complete for
PHP 8.5 language features». Пять SAPI (CLI, CGI, FPM, HTTP-обработчик,
запускалка тестов), двадцать расширений плюс демонстрационное `example`,
952 зарегистрированные функции без учёта демонстрационного.

Раздел README «Why?» называет четыре выгоды. Две из них в коде не
найдены: горутин и каналов, доступных из PHP, нет — поиск по `ext/` и
`core/` не даёт ни одной функции или класса с такой семантикой, горутины
служат только внутренней реализацией генераторов и Fiber; песочница
файловой системы через `fs.FS` существует как комментарий «so it can
later be scoped to an `fs.FS`» в `core/phpctx/global.go:2268` и
`core/phpv/context.go:197`, кода за ним нет.

## Устройство

Строки по подсистемам (без тестов):

| Подсистема | Строк |
|---|---|
| `core/tokenizer` | 2 215 |
| `core/compiler` (AST, обход дерева) | 32 191 |
| `core/vm` (байткод) | 8 821 |
| `core/phpobj` (объекты, генераторы, Fiber) | 11 910 |
| `core/phpctx` (процесс, глобальный контекст) | 7 340 |
| `core/phpv` (значения) | 6 107 |
| `core/stream` | 3 104 |
| `ext/` (двадцать расширений и `example`) | 87 906 |

Виртуальная машина — стековая, 278 опкодов в `core/vm/opcode.go`,
инструкция фиксированной ширины в 64 бита. Операторную семантику ВМ не
дублирует: обработчики опкодов зовут те же экспортированные помощники из
`core/compiler`, что и обход дерева. Значения на стеке — `*ZVal`, то есть
указатель на боксированное значение; `core/vm/doc.go` называет псевдоним
`Slot` швом для будущего перехода на распакованные значения. Отсюда и
скромный выигрыш ВМ над обходом дерева: таблица в README даёт от −43 %
до −74 % на пяти микротестах, и оба замера сделаны против самого себя.

Объекты держат счётчик ссылок (`ZObject.IncRef`/`DecRef`), деструкторы
срабатывают синхронно при обнулении счётчика, идентификаторы объектов
переиспользуются через список свободных. Циклы собирает сборщик Go,
поэтому наблюдаемый порядок разрушения местами расходится с Zend —
ROADMAP перечисляет расхождения и относит их исправление к «won't-do».

Расширения пишутся на Go: функция с магическим комментарием-сигнатурой,
`make buildext` порождает привязки. Расширений на C движок не принимает
ни в каком виде: `dl()` печатает «Dynamically loaded extensions aren't
enabled» и возвращает `false` (`ext/standard/base.go:33`).

SAPI тонкие: `php-cli` — 110 строк, `php-httpd` — 55, `php-fpm` — 46,
`php-cgi` — 39. FPM от одноимённого SAPI php-src берёт только протокол:
слушает жёстко зашитый `/tmp/php-fpm.sock`, менеджера процессов, пулов и
конфигурации у него нет. Файл `php.ini` не читается ни одним SAPI —
поиска по `core/ini` и `sapi/` на строку `php.ini` не находится вовсе;
371 директива существует как вкомпилированные умолчания, доступные через
`ini_set`/`ini_get`.

Наборы расширений у SAPI разные, и веб-сборки беднее консольной:
`php-cgi` и `php-fpm` не линкуют ни `mbstring`, ни `spl`, `php-httpd` —
не линкует `mbstring`.

## Полнота и как она проверена

Заявление README: 11 864 из 12 121 тестов набора PHP 8.5.5, около 97,9 %.
Проверка распадается на три вопроса — что считается знаменателем, как
считается процент и воспроизводится ли прогон.

### Знаменатель

12 121 — это все файлы `.phpt` в репозитории; счёт по `git ls-tree`
совпадает с заявленным точно. Состав:

| Область | Тестов |
|---|---|
| Zend/tests (ядро языка) | 5 290 |
| ext/standard | 3 811 |
| ext/spl | 782 |
| ext/date | 688 |
| ext/reflection | 493 |
| ext/mbstring | 416 |
| ext/pcre | 165 |
| ext/gmp | 99 |
| ext/json | 88 |
| ext/hash | 80 |
| ext/ctype | 49 |
| собственные тесты `test/basic` | 160 |

У php-src на теге `php-8.5.5` — 21 486 файлов `.phpt`, тесты лежат в 68
расширениях (снято через GitHub API по дереву коммита
`fb047060`, 29 августа 2026). Goro вендорит десять из них и не вендорит
верхний каталог `tests/` php-src (867 тестов). То есть знаменатель —
55,7 % набора, и отбор не случаен: одиннадцать расширений, которые goro
написал сам (curl, gd, session, sockets, zlib, mysqli, sqlite3, bz2,
xml, openssl), тестов в дереве не имеют. ROADMAP говорит об этом прямо:
«Not yet vendored … The extensions themselves are implemented, but the
upstream test suites aren't imported into the repo yet».

### Как считается процент

Прогонщик — своя реализация протокола `.phpt` на Go, файл `php_test.go`
на 1175 строк; `run-tests.php` из php-src в дереве лежит, но его зовёт
только скрипт `run-tests.sh`, а число в README берётся из Go-теста.

Итоговая строка (`php_test.go:1165`) считает `pass / (count − skip)`.
На числах README — 11 864 прошедших, 87 пропущенных, 12 121 всего — эта
формула даёт 98,59 %, а не 97,9 %. Значит, в README стоит `pass / count`,
то есть более строгое из двух чисел. Расхождение формул само по себе
безобидно, но показывает, что число в README снято не тем инструментом,
который его печатает.

Пропущенные тесты из знаменателя формулы выпадают, и попадают в пропуск
не только неподдерживаемые возможности. В `php_test.go:939` лежит
список из 87 путей, вычёркиваемых поимённо, и комментарии рядом с ними
называют причину: «Nil pointer in stream», «Stack overflow in fiber
destructor», «gopcre2 infinite loop on negative lookbehind», «Interface
conversion panic». Это падения движка, а не пробелы в возможностях.
Туда же уходят тесты с `XFAIL`, тесты с непонятой директивой INI,
тесты с неизвестной секцией `.phpt` и два каталога целиком
(`ext/standard/network/` и `*/gc/`).

### Воспроизводится ли

Нет. Документированная команда — `go test ./...`, как в CI, — на свежем
клоне падает.

Прогон 29 августа 2026, WSL Ubuntu 24.04, Go 1.25.3, `CGO_ENABLED=0`:
`go test -count=1 -run TestPhp .` обрывается через 16,9 секунды на 923-м
тесте с `fatal error: stack overflow`. Стек — бесконечная рекурсия
`FuncContext.Tick`. Тест — `test/php-8.5.5/bug73753.phpt`, он же падает
в одиночку за 1,6 секунды. Настоящий PHP 8.5.1 на том же коде печатает
`string(3) "baz"` мгновенно. Причина в семантике внутреннего указателя
массива: `next()` внутри `getNext(&$a)` не сдвигает указатель, условие
выхода из рекурсии не наступает, и рекурсия PHP переходит в рекурсию Go
без ограничителя глубины. Соседний метод `FuncContext.Loc` ограничитель
имеет, и комментарий над ним прямо называет причину — «a FuncContext-pool
aliasing bug»; у `Tick` такого ограничителя нет.

Второе падение того же рода — не крах, а зависание: `concat_003.phpt`
требует 220 000 конкатенаций уложить в 2 секунды, и прогон стоит на нём
дольше пятнадцати минут, пока его не снимает таймаут.

Сверить с их собственными прогонами нельзя: логи последнего запуска CI
(26 мая 2026) стёрты по сроку хранения, API отвечает HTTP 410. Все
последние 100 запусков workflow завершились неуспехом; последний
успешный — 19 апреля 2026. Неуспех сам по себе ожидаем — любой упавший
`.phpt` красит задачу, — но проверить по логам заявленное число уже
нельзя ни для одного коммита.

Чтобы обойти крах, я прогнал набор кусками по 500 тестов отдельными
процессами: падение убивает только свой кусок. Результат ниже.

### Сборка под Windows

Не собирается. `go build ./...` на windows/amd64 (Go 1.24.2, 29 августа
2026) даёт неопределённые `syscall.Access`, `syscall.Stat_t`,
`syscall.Umask` в `ext/standard/fs.go` и `syscall.SO_RCVTIMEO`,
`syscall.MSG_PEEK` в `ext/sockets/constants_other.go`. Кросс-сборка под
linux/amd64 из того же дерева проходит. `exec()` зовёт `/bin/sh -c`
без вариантов (`ext/standard/exec.go:93`).

## Экосистема

Composer не работает. Скрипт, который делает `require vendor/autoload.php`
и создаёт парсер `nikic/php-parser` 5.x, падает в самом автозагрузчике:

```
Fatal error: Uncaught Error: Access to undeclared static property
PhpParser\Lexer\Emulative::$includeFile in vendor/composer/ClassLoader.php:426
```

Причина не в библиотеке, а в разрешении `self::` при вложенном
автозагрузе. Сокращённое воспроизведение — шестнадцать строк:

```php
class Loader {
    public static $inc;
    public function load($class) {
        $f = __DIR__ . '/' . $class . '.php';
        if (!file_exists($f)) { return null; }
        $inc = self::$inc;   // <-- здесь
        $inc($f);
        return true;
    }
}
Loader::$inc = \Closure::bind(static function ($file) { include $file; }, null, null);
spl_autoload_register([new Loader(), 'load']);
$o = new C1();               // C1.php объявляет class C1 extends C2
echo get_class($o), "\n";
```

PHP 8.5.1 печатает `C1`. Goro на втором, вложенном вызове `Loader::load`
разрешает `self::` в `C1` — класс, который объявляет внешний `include`, —
и бросает «Access to undeclared static property C1::$inc». То есть `self`
связывается по динамическому состоянию, а не по лексическому классу
метода. Набор php-src теста такой формы не содержит, поэтому 97,9 %
про эту поломку ничего не говорят.

Даже если бы автозагрузчик работал, крупные фреймворки упираются в
отсутствующие расширения. Laravel требует ctype, curl, dom, fileinfo,
filter, hash, mbstring, openssl, pcre, pdo, session, tokenizer, xml —
из них в goro нет dom, fileinfo, filter (`filter_var` отсутствует), pdo и
tokenizer (`token_get_all` отсутствует), а mbstring не влинкован в
веб-SAPI. Нет также iconv, intl, Phar, ZipArchive, bcmath, `proc_open`,
`mail` и pcntl. Для WordPress mysqli есть, но собственный вендоренный
набор pcre проходит на 67 % — и это то расширение, на котором WordPress
держит маршрутизацию и шорткоды.

Скорости, ради которой стоило бы терпеть, нет. Сравнения с Zend в
репозитории нет ни одного: таблица README сравнивает ВМ goro с обходом
дерева goro. Мой замер (29 августа 2026; goro — Linux/WSL, PHP 8.5.1 —
Windows, релизная сборка, `-n`, та же машина; разные ОС, поэтому число
годится только как порядок величины):

| Тест | goro | PHP 8.5.1 |
|---|---|---|
| `$sum = $sum + $i`, 1 000 000 итераций | 0,298 с | 0,013 с |
| вызов замыкания, 200 000 раз | 0,550 с | 0,009 с |
| `fib(25)` | 0,390 с | 0,012 с |
| 200 000 `$a[] = $i` и обход | 0,162 с | 0,010 с |

Отдельно плохо с конкатенацией: она квадратична. Дописывание строки в
40 байт даёт 0,580 с на 10 000 повторов, 2,504 с на 20 000 и 7,476 с на
40 000; на 80 000 срабатывает вкомпилированный лимит в 30 секунд.
PHP на тех же входах — 0,000, 0,004, 0,002 и 0,005 секунды. Отсюда и
зависание на `concat_003.phpt`, который ровно это и проверяет.

## Почему не заметили

Инвентарь записал: «самый полный не-Zend PHP из живых, и полнота не
принесла ему пользователей». Первая половина держится с оговорками
(полнота измерена на 55,7 % набора и своим прогонщиком), вторая
подтверждается. Причины делятся на проверяемые и предположительные.

### Проверяемое

1. **Полноты, о которой идёт речь, снаружи не видно.** Число 97,9 %
   снято на отобранном подмножестве, посчитано не той формулой, которую
   печатает код, исключает 87 поимённо вычеркнутых падений движка, а
   документированная команда прогона на свежем клоне обрывается через
   17 секунд. Проверить заявление по логам CI нельзя — они стёрты.

2. **Composer не запускается.** Ошибка в разрешении `self::` при
   вложенном автозагрузе ломает `vendor/composer/ClassLoader.php`.
   Приложение, собранное после 2013 года, до первой своей строки не
   доходит.

3. **Расширений не хватает даже для списка требований фреймворка.**
   Нет PDO, dom, tokenizer, fileinfo, filter, iconv, intl, Phar, zip;
   веб-сборки не линкуют mbstring и spl. Расширения на C невозможны в
   принципе: `dl()` отключён, значит PECL закрыт навсегда, а не «пока».

4. **Выгоды при переходе нет.** По микротестам движок медленнее Zend без
   JIT в 15–60 раз, конкатенация строк квадратична. Две выгоды,
   обещанные в README — горутины и каналы из PHP, песочница `fs.FS`, —
   в коде отсутствуют; вторая существует как комментарий «later».

5. **Нечего установить и не на что сослаться.** Ноль релизов, ноль
   тегов, нет сайта, `pkg.go.dev` пуст, «Imported by: 0». Единственный
   способ попробовать — `go install` из master.

6. **Никто не звал.** Один твит автора в 2018 году; сабмишен на HN
   сделал посторонний; о перезапуске 2024–2026 годов не написано ни
   слова нигде. Ниша тем временем занята, и занявшие её проекты брали не
   полнотой, а входом в экосистему: Swoole в PECL с 24 декабря 2013
   года, RoadRunner выпущен Spiral Scout 24 апреля 2019 года, и оба
   вошли в Laravel Octane 1.0 11 мая 2021 года; FrankenPHP вошёл в
   Octane 19 декабря 2023 года и получил официальную поддержку PHP
   Foundation с переносом репозитория в организацию `php` 15 мая 2025
   года.

7. **Хозяина нет.** 1645 коммитов из 1924 — один человек, и работа
   дважды останавливалась на годы. У Swoole есть PECL и ведущий
   мейнтейнер, у RoadRunner — Spiral Scout, у FrankenPHP — Les-Tilleuls
   и PHP Foundation, у KPHP — VK. Контрпример здесь важен: у KPHP хозяин
   есть, а звёзд 1,5 тысячи и интеграций с экосистемой ноль. Значит,
   решает не владелец сам по себе, а вход в цепочку, которой люди уже
   пользуются.

### Предположения, не подтверждённые источниками

- **Репутационный фактор.** Публичных свидетельств ровно три, и все они
  показывают лишь порядок изложения: в треде HN 2018 года и в заметке
  PHP Magazine имя автора и Mt. Gox названы раньше кода. Ни одного
  высказывания вида «не беру из-за автора» я не нашёл. После 2024 года
  связь не проводил никто — но и обсуждений проекта не было, поэтому
  отсутствие связи ничего не доказывает в обе стороны.

- **Go как барьер.** Правдоподобно, что PHP-разработчик не станет
  чинить движок, написанный на незнакомом языке, но публичных
  высказываний на эту тему я нашёл одно — вопрос «зачем тогда PHP» в
  треде 2018 года, и он про другое.
